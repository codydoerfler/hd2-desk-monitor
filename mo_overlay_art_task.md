## The hard constraint: flash budget

Check current usage first (`pio run` on this branch, read the size report) —
last known figure was 96.7% of 4MB with the boot-overlay trigger change
already landed, so there is very little headroom, maybe on the order of
100-150KB, and that number may have shifted since. This is the real ceiling
on how much photographic detail can be embedded, and it needs to be treated as
a hard number to check against, not guessed at.

The codebase already has a working pattern for embedding real bitmap art
compactly: `src/hud_biomes.h`, PROGMEM `uint16_t` arrays generated by a
`tools/gen_*.py`-style script (check `tools/` for the actual generator and its
compression/encoding approach — likely RGB565 with some size-reduction scheme,
read it before reinventing anything). That pattern is the right tool here,
not a JPEG decoder — there is no PSRAM on this MCU (see `README.md`
hardware table) and pulling in a JPEG library plus decode buffers for a
one-off screen is very likely not worth it against 520KB SRAM. Follow the
existing bitmap pipeline's conventions.

To fit the reference art's photographic flag/skyline panel in whatever budget
is actually available, expect to need real image-processing judgment, not
just "make the JPEG smaller": crop tightly to the flag+skyline region actually
visible in the reference composition, downsample aggressively to whatever
resolution the panel's actual on-screen art area needs (compute this from
`layout::screenW`/`screenH` and the composition's proportions, don't guess),
reduce color depth/palette if the existing biome-art pipeline supports a mode
for that, and consider whether one shared background image can serve as a base
for both the success and failure variants (e.g. one photo, a color-grade/tint
pass at build time or at render time on-device) rather than embedding two full
separate photographic assets — that may be the difference between fitting and
not fitting. Use your own judgment on the right tradeoff, but the goal
Cody stated is visual closeness, so exhaust reasonable options before falling
back to a flattened vector reinterpretation the way the touch screens did.

If, after genuinely trying the above, the photographic art still cannot fit:
document exactly why (real byte counts, what was tried) in the PR, and fall
back to the closest reasonable native-drawn interpretation of the composition
(angled panel, correct accent colors, correct text hierarchy/position) rather
than silently keeping the old centered-card layout. Either way the layout
composition (left text panel / right art or accent field, angled divider)
should change to match the references — that's achievable regardless of
whether the art itself ends up photographic or drawn.
